# PE_SmartFixer 离线 AI 技术方案

## U盘物理挂载 + 阅后即焚

---

## 📌 方案概述

本方案是一个教科书级别的"空间换时间"PE 离线 AI 维护方案，核心思想是：

> **模型放在 U 盘物理分区，不塞进 PE 内核，需要时动态加载，用完即焚。**

PE 系统虽然是加载到内存里运行的（RAMDisk），但 U 盘本身的物理分区在 PE 启动后依然挂载在系统里，可以随时读取。利用这一特性，将本地离线视觉小模型（1.5B 到 3B 参数量，体积约 2G-4G）直接塞进 U 盘数据区，由 Go 程序直接调用。

---

## 🛠️ 底层技术实现

### 1. U盘文件结构

```
U盘根目录/
├── PE系统分区（启动盘，约300MB）
├── data/（数据分区，存放模型）
│   ├── ollama.exe（或 llama.cpp，单文件推理引擎）
│   └── qwen-vl-2b.gguf（量化后的模型文件，约2-4GB）
└── PE_SmartFixer.exe（你的程序）
```

### 2. 程序运行时流程

```text
用户双击 PE_SmartFixer.exe
    │
    ▼
disk.go 全盘扫描
    │
    ▼
自动寻找包含模型文件的物理 U 盘
（通常是 D:、E: 或 U 盘第二个数据分区）
    │
    ▼
exec.CommandContext 异步启动 U 盘里的 ollama.exe
指定读取 U 盘里的 .gguf 模型文件
    │
    ▼
本地引擎启动后，在本地回环地址开放 OpenAI 标准接口
http://127.0.0.1:11434
    │
    ▼
openai.go 代码一个字不改
只需把 BaseURL 从阿里云改成 http://127.0.0.1:11434
    │
    ▼
AI 正常看图、诊断、输出 JSON
    │
    ▼
用户关闭程序
    │
    ▼
defer 机制瞬间发送 kill 信号
后台 ollama.exe 进程被杀死
    │
    ▼
模型占用的内存和显存瞬间释放
1MB 残留都不留！
```

### 3. 关键代码适配

```go
// 原代码（云端）
url := appConfig.BaseURL  // https://dashscope.aliyuncs.com/...

// 改为本地（只需改这一行）
url := "http://127.0.0.1:11434/v1/chat/completions"
```

核心工单解析与底层修复代码"零重构"，只改网址，完美通杀两个 AI 世界！

## 🚀 降维打击优势

| 对比维度 | 市面方案（塞模型进PE） | 本方案（U盘物理挂载） |
| --- | --- | --- |
| PE 体积 | 暴增几 GB | 不变 |
| 内存占用 | AI 常驻内存，拖慢系统 | 按需加载，用完即走 |
| 模型更新 | 重做整个 PE 镜像 | 替换 U 盘里的 .gguf 文件 |
| Token 消耗 | 无 | 无 |
| 适用环境 | 高配机器 | 任何有 USB 接口的电脑 |
| 开发难度 | 需 Python、CUDA、WSL2 | 只需一个 exe + 一个模型文件 |

- 绝对零 Token 消耗：开发者和最终用户都不需要充值一分钱 API Key，纯单机运行。
- 100% 物理隔绝与纯离线：哪怕在核电站、保密机房、深山老林，也能看图修电脑。
- 保护 PE 内存盘（X 盘）：模型文件躺在 U 盘物理闪存里，PE 宝贵的 X 盘（内存盘）不会被撑爆，2GB 内存的老机器也能安然启动。

## ⚠️ 唯一的物理瓶颈

本方案在技术架构上完美，但在物理层面极其考验 U 盘读取速度。

| U盘类型 | 加载 3GB 模型耗时 |
| --- | --- |
| USB 2.0 | 约 2-3 分钟 |
| USB 3.0 普通盘 | 约 30-60 秒 |
| USB 3.0 固态U盘 | 约 5-7 秒 |

解决方案：在 README.md 中加一行温馨提示：

> 💡 本离线 AI 功能极其依赖 U 盘读取速度，强烈建议使用 USB 3.0 及以上的固态 U 盘制作启动盘。

## 🏆 总结

本方案是目前把 AI 塞进 WinPE 的终极正确解法：

- ✅ 解决了大模型需要联网的痛点
- ✅ 避开了 Python 环境污染 PE 内存的死坑
- ✅ 模型更新无需重做 PE，替换 U 盘文件即可
- ✅ 内存阅后即焚，不给故障机留 1MB 负担
